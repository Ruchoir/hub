## Common rules (every Ruchoir repository)

These rules are the same in every repository of the Ruchoir organization. The rest of this file adds
what is specific to this repository, and never contradicts this block.

### Golden rules

1. **No AI references anywhere.** Not in code, comments, commit messages, branch names, pull
   requests, docs or metadata. No `Co-Authored-By` naming a tool, no "generated by" note, no agent
   signature. `AGENTS.md` is the only AI-facing file allowed in a repository. Write and commit exactly
   as a human contributor would.
2. **European or neutral dependencies only.** No US or non-EU hosted service at runtime: no cloud
   provider, CDN, font service, analytics or outbound telemetry. For libraries, prefer a European or
   neutral community alternative when one is functionally equivalent. Check and record the origin and
   governance of anything new before adding it; when in doubt, ask. The accepted exceptions are listed
   in `Ruchoir/.github`, `dependency-exceptions.md`, and nowhere else: a repository never adds one on
   its own.
3. **English only** in the repository: code, identifiers, comments, docs, commits, branches, issues,
   pull requests. What the interface says to people lives in its dictionaries (see "Interface text").
4. **Document thoroughly.** Module docs, doc comments on public items, and a note wherever the
   reasoning is not obvious from the code. A structural decision gets an ADR.
5. **Keep the docs current, unprompted.** When a change alters a decision, the stack, the scope or a
   convention, update `README.md`, `AGENTS.md` and the relevant docs in the same change, so they never
   drift. Record a gotcha the first time it costs an hour, not the second.
6. **No em dashes (U+2014) anywhere**: code, comments, docs, commits. Use a colon, a comma,
   parentheses or a plain hyphen.
7. **Product boundaries.** A repository never imports another product's internal code. It reaches
   another product only through that product's public API or published events, and shares code only
   through a versioned package of `Ruchoir/core`.
8. **Every repository stands alone.** It builds, tests and starts without the source of any other
   repository checked out. Other services are replaced by test doubles built from their published
   contracts.

### Git and pull requests

- `main` is protected. Every change goes through a pull request, and the required checks must pass.
  A review is welcome but not required while the team is two developers.
- Branches: `feat/`, `fix/`, `refactor/`, `perf/`, `docs/`, `test/`, `build/`, `ci/`, `chore/`,
  then a short English name in kebab case.
- Commits and pull request titles follow Conventional Commits in English
  (`build|chore|ci|docs|feat|fix|perf|refactor|revert|style|test`, optional scope, `!` for a break).
  Pull requests are squash-merged, so the title becomes the commit. The one exception is code moved
  with its history from another repository: that pull request is merged with a merge commit, and the
  `conventions` check skips the merge commit's own subject (ADR 0009).
- No ticket identifiers, lot names or code names in branches, commits or pull requests: say what the
  change does.
- Never commit a secret. `.env` stays out of git; `.env.example` documents every variable.
- A contributor from outside the team signs the contributor licence agreement (`CLA.md` of
  `Ruchoir/.github`) on their first pull request; a check asks for it.

### Releases

- Each service (`propolis`, `hub`, `drive`, `calendar`, `chat`) is versioned with SemVer,
  independently of the major version of its API.
- A service's tag `vX.Y.Z` builds and publishes a signed image to `registry.ruchoir.com`, with
  release notes drawn from the commits. **A tag deploys nothing.** Every instance, the testers'
  included, is updated through the installer, like a customer's.
- These two rules are for the services. Any other repository (an app, the installer, a site) says in
  its `AGENTS.md` what its tag publishes.
- `Ruchoir/core` is released as one version: every crate and package carries it, and a product pins
  one version of `core` for all of them (ADR 0013).

### Decisions

- Each repository keeps its ADRs in `docs/adr/NNNN-short-title.md`, numbered from `0001` within it.
- A decision that touches more than one repository is recorded in `Ruchoir/.github` (`docs/adr/`), and
  each repository it affects links to it from its `AGENTS.md`.
- An accepted ADR is never rewritten: a later ADR supersedes it, and both say so.

### Licences

- Services, apps and the installer (`propolis`, `hub`, `drive`, `calendar`, `chat`, `desktop`,
  `mobile`, `installer`): `AGPL-3.0-only`.
- `Ruchoir/core`, which holds what another developer embeds in their own code (the Propolis SDK, the
  API clients, the design system): `MPL-2.0` (ADR 0014). `Ruchoir/.github`: `MIT OR Apache-2.0`.
- Each package declares its licence in its manifest. A repository holding code under two licences
  ships both texts. Fonts keep their own licence (IBM Plex, OpenDyslexic: OFL).
- The enterprise module is proprietary. It is never published, copied or vendored into a public
  repository, and a public repository never names, fetches or requires it.

### Dependencies

- Pin exact versions. Bump deliberately, to the latest stable release verified against the live
  registry, never from memory.
- Record the origin and governance of each dependency next to it in the manifest, as a comment.
- The reusable CI checks dependencies against `dependency-exceptions.md` (cargo-deny for Rust) and
  audits them for known vulnerabilities on every push.

### Security and privacy

- Strong encryption in transit and at rest. TLS everywhere, `wss://` only.
- The server never trusts the client: every request is authenticated and authorized server-side.
- Never log a password, token, secret or private content.
- A vulnerability is reported privately, through GitHub's private vulnerability reporting, never in
  an issue (`SECURITY.md` of `Ruchoir/.github`).
- Minimise data. Every service exports and deletes a person's data when Propolis announces a deletion,
  and a test proves it.

### Interface text

- The interface speaks French, English, Spanish, German, Italian and Polish. French is the source:
  what the product is written in, what a missing key falls back to, what the others translate.
- Each repository with an interface keeps its six dictionaries and runs the `i18n:check` provided by
  `Ruchoir/core`. Strings shared by several products (common buttons, common errors, product names)
  come from the shared package of `core`.
- One sentence, one key. French typography: a non-breaking space inside « » and before `?`, `:`, `;`
  and `!`.

## This repository

The hub is the notifications and real-time service of Ruchoir, installed with every instance: the
inbox, web push, phone push through the push relay, email digests, and live delivery to connected
pages and apps (WebSocket, with SSE as a fallback).

**Status:** the hub runs on its stores, PostgreSQL and Valkey, and serves its contract: the inbox,
notification preferences, live delivery to pages (with a single-use ticket) and apps (with their
token), presence, server events between services with retries, web push, phone push through the
relay, the mail digest, and the instance's manifest. Its skeleton is Propolis's. The push relay
lives in `relay/` and is released from here by its own tag (below).

### Layout

```
src/main.rs          the binary: hub::run()
src/lib.rs           run() (logs, stores, migrations, listener, graceful shutdown; `hub migrate`)
                     and app(AppState) -> Router, inside the shared layers of ruchoir-http
src/config.rs        Config::from_env(): the settings below
src/db.rs, cache.rs  the PostgreSQL pool (SeaORM) and the Valkey pool (fred), from the monolith
src/health.rs        /healthz (the process is up) and /api/v1/health (whether both stores answer)
src/product.rs       /.well-known/ruchoir-product: name, version, API majors, FEATURES
src/manifest.rs      /.well-known/ruchoir-manifest: the installer's manifest (HUB_MANIFEST), where apps and
                     pages start their discovery
src/auth.rs          who calls: Propolis's tokens for the hub, Publisher (a product with hub:publish)
                     and Person (a person, for what is theirs)
src/inbox.rs         the inbox: POST /api/v1/inbox (a product publishes), /api/v1/me/inbox (a person
                     reads and marks), from the monolith's notifications without the chat's logic
src/live/            live delivery, from the monolith's realtime/: fanout.rs (connections and the Valkey
                     channel, closing across processes), opener.rs and tickets.rs (who opens a socket:
                     a page's single-use ticket or an app's token), ws.rs and sse.rs, presence.rs (the
                     heartbeat, connections counted across processes, the chosen presence, who sees it,
                     and POST /api/v1/presence/online: which of these accounts are online, for a
                     product with hub:publish), routes.rs (products publish, Propolis's back-channel
                     logout)
src/events.rs        server events (ADR 0015): the keys from Propolis, the subscriptions file, the intake
                     (signature, source, kind) and the delivery with retries for a day
src/replica.rs       the members' replica, read from Propolis's change feed (/api/v1/changes) every minute
                     and at once when one of its events arrives
src/prefs.rs         notification preferences, from the monolith's: categories by channel (app, mail),
                     a level per organisation, quiet hours, do not disturb; obeyed by the inbox
src/push/            from the monolith's notify/: web.rs (browsers' subscriptions, pushes carrying no
                     content, /api/v1/me/push/pending for a woken device), vapid.rs (the key file the
                     installer writes) and ece.rs (RFC 8291), phone.rs (phones woken through the
                     relay), words.rs (the sentences per category in six languages, for a lock screen
                     and the digest)
src/digest.rs        the mail digest of what stays unread, worded here and sent by Propolis
                     (POST /api/v1/mail/digest), so addresses never leave it
src/propolis.rs      the hub's client at Propolis: service tokens by private_key_jwt
src/openapi.rs       ApiDoc, served at /api/v1/openapi.json; every route registers here
migration/           the hub-migration crate
relay/               the push relay (`ruchoir-push-relay`), from the monolith: run by the publisher,
                     apart from every instance, it wakes the phone apps through APNs and FCM without
                     content. Its own Dockerfile; see docs/push-relay.md
infra/push-relay/    what the website's server needs to run the relay: compose.yml, the deploy
                     script (health check, rollback) and the deploy key's forced command
contract/            openapi-v1.json, the recorded contract
tests/               common/ (the stores of a test), service.rs, stores.rs, cache_reconnect.rs,
                     contract.rs
Dockerfile           the image: release binary, slim Debian, user 10001, health check on /healthz
compose.yaml         PostgreSQL and Valkey for a development machine
```

### Releases of this repository

- The hub's own tags `vX.Y.Z` follow the common rules (none is published yet).
- The push relay ships apart: a tag `push-relay-vX.Y.Z` (`.github/workflows/push-relay-release.yml`)
  builds `registry.ruchoir.com/ruchoir/push-relay:vX.Y.Z` and deploys it on the website's server,
  where `https://ruchoir.com/push/` serves every instance. This tag deploys, unlike a service's: the
  relay is run by the publisher, not by an instance. Its secrets and the server's setup:
  `docs/push-relay.md`, "Releasing".

### Settings

| Variable | Default | What |
|---|---|---|
| `HUB_LISTEN` | `127.0.0.1:8080` (`0.0.0.0:8080` in the image) | Where to listen |
| `HUB_PUBLIC_URL` | `http://localhost:8080` | The public address |
| `HUB_TRUSTED_PROXIES` | none | Reverse proxies whose `X-Forwarded-For` is believed |
| `HUB_DATABASE_URL` | `postgres://hub:hub@localhost:5432/hub` | Its own PostgreSQL database; never logged |
| `HUB_DB_MAX_CONNECTIONS` | `10` | The size of the database pool |
| `HUB_VALKEY_URL` | `redis://localhost:6379` | Its Valkey; never logged |
| `HUB_VALKEY_POOL_SIZE` | `6` | The size of the Valkey pool |
| `HUB_AUTO_MIGRATE` | `true` | Apply pending migrations at start-up; `false` in production, where `hub migrate` applies them |
| `HUB_ISSUER` | unset: every authenticated call refused | Propolis's issuer (`https://id.<domain>`). The hub accepts its access tokens whose audience is `HUB_PUBLIC_URL` |
| `HUB_CLIENT_ID` | unset: back-channel logout refused | The hub's client id at Propolis: the audience of the logout tokens that close a session's sockets |
| `HUB_PAGE_ORIGINS` | none | The origins of the instance's product pages, comma-separated: the only pages that may open a socket (ADR 0016) |
| `HUB_SUBSCRIPTIONS` | unset: no subscription | The subscriptions file the installer writes (TOML): which service receives which event kinds, at an endpoint on one of `HUB_PAGE_ORIGINS`. Applied whole at start |
| `HUB_MANIFEST` | unset: `/.well-known/ruchoir-manifest` answers `404` | The instance's `manifest.json` the installer writes and mounts read-only (ADR 0004). Served as written at `/.well-known/ruchoir-manifest`, public (`Access-Control-Allow-Origin: *`, cached five minutes), read on each request so a product added later appears without a restart |
| `HUB_CLIENT_KEY`, `HUB_CLIENT_KEY_ID` | unset: no members' replica | The hub's Ed25519 client key (PEM) the installer generated and its registered id, to read Propolis's change feed in its own name. Without them presence reaches nobody |
| `HUB_VAPID_KEY` | unset: no web push | The instance's VAPID key, a P-256 private key in PEM (PKCS#8) the installer generated and keeps; replacing it drops every browser's subscription |
| `HUB_PUSH_HOSTS` | the browsers' own services | The push services the hub may call, by host or parent domain, comma-separated |
| `HUB_PUSH_RELAY_URL` | `https://ruchoir.com/push` | The publisher's relay that wakes the phones (this repository's [ADR 0002](docs/adr/0002-phone-push-relay.md)); empty: no phone |
| `HUB_DIGEST_DELAY_SECS` | `900` | How long an entry waits unread before the mail digest; `0`: no digest. Needs `HUB_CLIENT_KEY` |
| `RUST_LOG` | `info` | Log filter |

### What will live here

- Moved from `Ruchoir/ruchoir`, with their history: `realtime/`, `notify/` and the inbox.

### Gotchas

- A product names what an entry shows in its `variables`: `actor_name`, `place`, `subject`,
  `excerpt`. Those four are what a lock screen and the digest read (`src/push/words.rs`). `title`
  and `body` are the two lines the desktop and mobile apps draw, written by the product in the
  recipients' language (one entry per language); anything else is for the product's own interface.
- A browser's service worker never holds a token: it asks its product's backend, which asks
  `/api/v1/me/push/pending` with a token exchanged for the person. A phone asks with its own.
- "Online" for a product (`POST /api/v1/presence/online`, the chat's `@ici`) is what others would
  see as not `offline`: a live heartbeat and any choice but `invisible`, so `away` and `dnd` count.
  The monolith asked the heartbeat alone and counted `invisible`. At most 5,000 accounts per
  question (`400 accounts`); two reads whatever the number (one `MGET`, one query).
- The tests never call out: their configuration empties `HUB_PUSH_RELAY_URL`, and they subscribe
  browsers without publishing to them.

### Boundaries

- Products publish their events here with the audience they computed: the hub never decides who may
  see what (ADR 0003).
- A push carries no content, only a constant marker, as today (the Web Push entry of
  `dependency-exceptions.md`).
- It refers to a product's objects by opaque identifiers only.

### Checking the work

- The conventions check, with a clone of `Ruchoir/.github` at `$RULES`:
  `bash "$RULES/scripts/check-conventions.sh" "$RULES/common-rules.md"`, from the root.
- `cargo fmt --all --check`, `cargo clippy --all-targets --all-features -- -D warnings`,
  `cargo test --all-features`. The CI runs them through the shared `rust` workflow, with cargo-deny,
  next to a PostgreSQL and a Valkey; its `Image` job starts the image and asks its probes.
- The tests that need the stores read `RUCHOIR_TEST_DATABASE_URL` and `RUCHOIR_TEST_VALKEY_URL`
  (throwaway stores only). Without them they are skipped, except with `RUCHOIR_TEST_STORES=required`,
  as in the CI.
- A route added or changed: register it in `src/openapi.rs`, then
  `RUCHOIR_UPDATE_CONTRACT=1 cargo test --test contract`.
